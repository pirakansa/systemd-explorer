# Publishing a release

The **Release** GitHub Actions workflow is started manually with `workflow_dispatch`. It reads the root package version from `Cargo.toml` through `cargo metadata`; there is no separate version input or automatic version bump.

## Run the workflow

1. Set `[package].version` in `Cargo.toml` to the intended SemVer version. Refresh `Cargo.lock` with Cargo if needed, and merge the changes to `main` through a PR.
2. Open **Actions → Release → Run workflow**, select **main**, and start it.
3. After validation and both native builds succeed, the workflow creates the lightweight tag `v<version>` at the exact commit selected by that workflow run, uploads assets to a draft GitHub Release, then publishes it.

For example, `version = "0.1.0"` produces tag `v0.1.0` and these assets:

- `systemd-explorer-v0.1.0-linux-amd64.tar.gz`
- `systemd-explorer-v0.1.0-linux-arm64.tar.gz`
- `SHA256SUMS`

Each archive contains a directory named after the archive, with the collector executable, `viewer/` (including fictional samples), `docs/`, README and license. The viewer remains static and requires no Node.js installation. Download an archive and `SHA256SUMS` into the same directory and run `sha256sum --ignore-missing --check SHA256SUMS` before extracting it.

A SemVer prerelease such as `0.2.0-rc.1` is marked as a GitHub prerelease. Build metadata alone, such as `0.2.0+build-1`, does not make it a prerelease. Release notes are generated by GitHub.

## Build and publication behavior

The workflow reuses the CI quality gates (`vorbere run check`, `vorbere run test`, `vorbere run build`) before packaging. It additionally runs Rust tests, release builds and the executable's help command natively for each target:

| Asset architecture | Rust target | GitHub-hosted runner |
| --- | --- | --- |
| amd64 | `x86_64-unknown-linux-gnu` | `ubuntu-24.04` |
| arm64 | `aarch64-unknown-linux-gnu` | `ubuntu-24.04-arm` |

These are GNU/Linux binaries built on Ubuntu 24.04, with dynamic glibc dependencies; they are not fully static musl binaries. Use a compatible glibc-based distribution or build from source on the target distribution. The repository must have access to the listed GitHub-hosted runners, including ARM64.

Only the publication job receives `contents: write`; other jobs have read access. The standard `GITHUB_TOKEN` is used, so no personal access token is required. Repository permissions and tag rules must allow this workflow to create release tags. Starting the workflow on any branch other than `main` fails before build/publication. The workflow file must be present on the default branch for GitHub to expose its manual trigger.

Concurrent release runs are serialized. Existing tags are rejected before builds, and the final tag-creation API call also refuses to replace an existing tag. A failed test/build does not create a tag. Uploads happen while the release is a draft, and publication happens only after the upload command succeeds.

## Retry a failed publication

A publication failure can leave a new tag or a draft release because GitHub's tag, upload and publish operations are separate API requests. The workflow deliberately does not delete tags, overwrite assets or resume an existing release automatically. Inspect the failed run and draft first. If nothing was published, a maintainer can finish the draft manually or remove that draft and its unpublished tag before rerunning the same version. For an already published version, bump the manifest version and make a new release.

## Local verification

`vorbere run test` includes tests for root-package version selection, stable/prerelease detection, invalid release identifiers and exact workflow output generation. The native ARM64 build, GitHub permissions, tag creation and actual release publication require a GitHub Actions run; local fixture tests do not establish those results.
