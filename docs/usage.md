# User guide

## Collect on the Linux machine

Build with `cargo build --release`, or transfer a compatible compiled binary. Use an ordinary user account:

```bash
systemd-explorer collect --output snapshot.json
systemd-explorer collect --output later.json --timeout-seconds 180 --command-timeout-seconds 5
```

The output path must not already exist. The parent directory must exist and be writable. JSON is serialized into a temporary file in that directory and published without overwriting an existing file. On Unix, the output is owner-readable/writable (0600). The collector writes only its output and temporary capture files; it does not change unit files, enablement or service state. It does not elevate privileges or prompt for credentials.

The default external-command budget is 120 seconds and each command is limited to 10 seconds. Both flags accept 1–3600 seconds. Disk enumeration checks the remaining budget between entries; ordinary filesystem I/O and final normalization/serialization are not a hard real-time deadline. Each command's captured stdout+stderr is bounded to 32 MiB (checked every 20 ms), and individual file reads are limited to 256 KiB. At most 50,000 loaded and 50,000 installed inventory entries are processed. Limits or collection errors produce warnings.

`systemctl`, `systemd-analyze` and `udevadm` must be discoverable through `PATH`. Use a trusted PATH. The collector uses separate argument arrays, never a shell. Collection is limited to the **system manager**, not user managers or remote systems.

Exit status 0 means the snapshot was written, including when collection was partial or unavailable. Check `metadata.diagnostics` and `warnings`, not just the exit code. Invalid arguments, serialization errors and output failures return nonzero. A system without systemd can still yield a diagnostic snapshot with no units.

## Transfer and inspect offline

Copy `snapshot.json` and the entire `viewer/` folder to the viewing PC. No HTTP server, Node.js installation or access to the Linux machine is required. Open `viewer/index.html` directly in a modern desktop browser, then use **Open snapshot** or drag/drop. The viewer uses local file APIs and does not make network requests. The optional documentation link requires copying `docs/` alongside `viewer/`.

1. Read the overview counts and collection diagnostics. Boot ID and collection interval identify context; the snapshot is not atomic.
2. Search by unit name or description, then filter by type or active state. `unknown` includes installed units with no runtime observation and unresolved references. Inventory results are loaded in pages of 100.
3. Select a unit. The default **Relationship list** shows direct references: **Referenced by** on the left (other unit → selected unit) and **References** on the right (selected unit → other unit), with the selected unit between them. Narrow windows place the selected unit above the lists or stack the columns. Names wrap in full and rows show observed type/state. Each direction is grouped by relation kind and evidence layer; group headings count distinct units and observation records separately. Multiple observations for the same unit/kind/evidence share a row, with every source preserved in details. Scroll each column and use **Show more units** to load groups in pages of 40. Graph caps do not limit these lists.
4. For busy targets, enable **Activation requests only** to restrict both views to `Requires`, `Wants`, `BindsTo` and `Upholds`. Enable **Active only** to retain only related units whose observed `active_state` is exactly `active`; both options can be combined. These are Viewer controls: existing snapshots already contain the necessary data, so no collection option or recollection is needed. The selected unit is always retained even if inactive or unknown. The list counts excluded direct neighbors; graph traversal stops at excluded units without inventing shortcut connections. Filtering happens before graph size caps. Inventory, timeline and full detail relationships remain available.
   Toggle effective, disk-symlink and installation-hint layers, then individual relation kinds to narrow further. Non-request kind controls are disabled while the request filter is enabled; disabling it restores previous individual selections. Disk clues remain distinct from effective manager relationships in both views. Request kinds do not make disk hints effective, and active observations do not prove enablement or the cause of startup.
5. Use **Search related units** to match full names or descriptions in both direct-reference lists, including rows not loaded yet. This search does not filter the inventory or graph. Click any related unit to make it the focus; the related-unit search clears on navigation. Direct lists stay at one hop: follow rows to explore further. The controls do not infer causal or chronological direction from property arrows, so `After` still does not start another unit.
6. Switch to **Graph (N hops)** for a small supplementary graph, with both incoming and outgoing edges to the chosen hop limit (0–4). Nodes are arranged in spaced depth columns and reset at full text size; the viewport scrolls instead of automatically shrinking the entire graph. Scroll to move through the viewport, drag to pan, use Ctrl/⌘ + scroll or buttons to zoom, and click nodes to navigate. The displayed graph is capped at **25 nodes / 80 edges** and announces truncation. Narrow the neighborhood or disable layers; the relationship list and details retain access to all direct observations. Inventory filters do not hide other types in either relationship view.
7. Inspect paths, reload hints, unassigned origins, device/udev properties, per-unit times and warnings in details. All collected relations remain available there in pages of 100, regardless of view filters. There is no automatic explanation of the full activation cause.
8. Use **System timeline** above the unit explorer to inspect all available transition observations. Its overview histogram covers the entire snapshot, including late restarts; counts represent timestamp observations, not active-unit counts. Drag a range in the overview or set **From/To (seconds)** and **Apply range**. **Zoom in/out**, **Earlier/Later** and **Full range** adjust the detailed window. For a late outlier, enter a narrow range such as 0–30 seconds to inspect early boot observations.
9. Timeline rows are grouped by unit type and ordered by their earliest retained observation, followed by units with unknown timing. This is an observation order, not proven startup order. Collapse/expand a type or all types, search full unit names/descriptions, and scroll vertically. Only visible rows are mounted in the browser; there is no 200-observation display cap. A unit with known timestamps appears if at least one falls inside the chosen window. **Show units with unknown timings** controls rows with no comparable timestamps; unknown rows are not positioned as if they started at zero. Counts report missing units and unknown/incomparable records separately.
10. Each colored point is an observed inactive-exit, active-entry, active-exit or inactive-entry transition. Hover for the precise event time/source and click the unit name to open its relationships/details. Row state is the collection-time state, not a reconstructed state at the selected time. No interval bars or blame-style startup durations are inferred from these latest timestamps. Very long timeline names are limited to two lines with the full name in the tooltip; relationship lists and details preserve the full name. A changed boot ID suppresses the shared timeline. Timeline controls are independent of inventory and relationship filters.

Long graph labels are truncated visually; the relationship list, inventory and details retain full names. The browser input limit is 100 MiB and one million records per top-level collection; very large snapshots can still take time to index.

## Troubleshooting

- **Cannot connect to bus / manager:** verify that the source machine boots systemd as PID 1 and the system bus is accessible. A container without systemd is not a substitute for host collection.
- **JSON inventory unsupported:** the collector detects failure or invalid JSON and falls back to name/load/active/sub columns with locale C and headers/pager/colors disabled. Unit properties still use the `key=value` interface; descriptions are never extracted from the fallback display.
- **Permissions or command missing:** the available inventory is preserved; the affected item is marked unavailable. A failed property batch is retried per unit while budget remains. Do not assume root is necessary.
- **Unit listed as installed with unknown state:** properties are queried only for units already in the loaded inventory. Inspecting an unloaded unit through `systemctl show` can cause it to load, so this collector avoids that query. A unit can disappear between inventory and inspection; collection cannot eliminate this race.
- **Missing timestamps or device mapping:** older versions, garbage-collected units, permission limits and never-observed transitions are possible. Read the diagnostic instead of inferring a cause.
- **Unsupported schema / malformed JSON:** the viewer explains the error and clears stale results. Unknown optional fields in version 1 are accepted; future schema versions are rejected explicitly.

## Inspect placement prerequisites

The selected unit's details now include effective activation-request paths (Wants, Requires, BindsTo, Upholds), normalized ordering neighbors, and local device/mount/trigger contacts. Paths explore at most four upstream request hops and 100 queued paths; cycles or limits are reported. They identify candidate request chains, not the actual historical activation cause. Before and After are normalized for the ordering lists and do not imply startup requests or application readiness.

Hardware contacts retain original effective edges within two undirected hops, capped at 100 visited nodes and 100 displayed edges. They are not sysfs parent/child relationships or a device readiness trace. Use the existing per-device sysfs/udev details for collected clues. Exact rule origins, application readiness, initial boot history and configuration attribution remain unimplemented; this iteration improves exploration using existing snapshots without extending collection.

The **Startup, conditions and result** section displays service startup semantics and latest results, plus mount source/point mappings. To obtain these new fields, collect a new snapshot with the updated binary. Existing snapshots still open and display unknown for missing fields. Conditions and asserts without an evaluation timestamp must not be treated as evidence of this activation's condition checks; service state and result do not by themselves prove application readiness. Sensitive-looking mount sources are omitted rather than exported.
